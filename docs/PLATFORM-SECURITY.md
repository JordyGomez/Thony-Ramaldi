# Seguridad e integridad empresarial

- SUPERADMIN se comprueba por UID y correo verificado en tablas protegidas, no por nombre, dominio, perfil ni valores recibidos del navegador. El administrador personal no lo hereda.
- API del mismo origen, sesión real comprobada en servidor y nueva autorización en RPC/RLS. Ninguna API acepta un nombre arbitrario de función SQL. Las acciones admitidas y sus campos están cerrados.
- Cambios de modo, edición, aprobación, incorporación y permisos son transaccionales. Bloqueos y versiones detectan concurrencia; ni una propiedad ni un perfil se publican por manipular un booleano del formulario.
- Las nuevas tablas privadas tienen RLS y lectura únicamente del propio registro o de los revisores autorizados; clientes sin DML directo. `platform_state` permite leer solo ID, modo activo y revisión, que ya son información pública. Autor/fecha y auditoría no son columnas públicas.
- La política restrictiva de propiedades impide que una política permisiva anterior exponga borradores empresariales. El trigger impide DML empresarial directo desde `anon`/`authenticated`; las escrituras autorizadas usan RPC. Datos antiguos siguen con organización y agente nulos.
- La habilitación pública del perfil es independiente de sus borradores: ocultarlo retira también el inventario asociado y guardar otro borrador no lo reactiva. La autorización corporativa se vuelve a comprobar al leer el snapshot.
- Las funciones con privilegios fijan `search_path`, usan referencias calificadas y tienen EXECUTE limitado. `platform_log` no es invocable por clientes. El hook de altas solamente puede ejecutarlo `supabase_auth_admin` o el propietario de la base.
- Configuración corporativa y perfiles validan tipos, tamaño, contactos, rutas y listas de campos en servidor y SQL. React representa texto; no se acepta HTML, scripts ni CSS arbitrario. No se exponen borradores o historial en el snapshot.
- Invitaciones de 256 bits, almacenadas como SHA-256, ligadas a correo, caducidad y consumo de un solo uso. Límite de creación por administrador, revocación y auditoría. La verificación de correo y CAPTCHA dependen de Supabase Auth configurado; no se simula pertenencia por tener cuenta.
- `properties` conserva su bucket público y biblioteca anterior. El bucket nuevo `platform-media` es privado, con rutas `organización/UID/UUID.ext`, máximo 3 MB y tipos admitidos. La API verifica firma/tamaño, rol y destino; las políticas restrictivas impiden sustitución/borrado incluso ante concesiones antiguas amplias. Los agentes no usan la biblioteca personal.
- Los archivos empresariales se sirven mediante una ruta que comprueba referencias públicas aprobadas o permisos privados. Storage vuelve a aplicar RLS antes de emitir una URL firmada de 60 segundos. Esas URLs pueden seguir válidas hasta su expiración; no se promete retirar bytes ya descargados.
- Documentación privada no aparece en el snapshot. Solo los planos marcados para publicación se incluyen cuando la ficha queda aprobada/publicada. Añadir o retirar documentación exige nueva revisión; retirar no borra el objeto de Storage.
- No hay claves `service_role`, empleados ficticios ni anuncios creados en producción. Los usuarios, tokens y datos sintéticos se limitan a procesos de pruebas en loopback, bloqueados en Vercel.

La revisión de las políticas reales y la configuración de Auth/Storage del proyecto gestionado sigue siendo una operación del propietario de Supabase. Las pruebas aisladas verifican los archivos versionados; no demuestran que el dashboard real tenga instalado el SQL o conectados el hook, SMTP y CAPTCHA.
